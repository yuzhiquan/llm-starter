# 第 7 篇精读｜推理与 KV Cache：按下回车后的这一秒

> 原文：llm-07-inference.md ｜ 前置：第 6 篇 ｜ 核心一句话：推理 = Prefill 一次吃完全部输入 + Decode 一次吐一个 token，KV Cache 让 Decode 不必重算历史。

## 0. 三句话抓住它

- 第一个字慢是 Prefill，后面快是 Decode，不是动画。
- KV Cache 用显存换计算：每步只算新 token，不重算历史。
- 代价是显存随长度线性涨，128K 上下文能吃掉 64GB。

## 1. 这一篇在补哪个洞

第六篇结尾把训练收在一句话上：所有参数都固定了，模型可以用了。但它留下一个非常具体的疑问——你按下回车，到第一个字蹦出来，中间那几百毫秒在干什么？为什么第一个字等得久、后面却越来越顺？如果模型一次只能预测一个 token，那它是不是每吐一个字都要把前面所有内容重新读一遍？

本篇回答的就是这三个问题，核心答案是**自回归（autoregressive）解码**与 **KV Cache**。前者解释了"为什么要循环"，后者解释了"为什么循环没有变慢"。理解这一篇，你就能算清楚一次请求的延迟花在哪、显存花在哪、长上下文为什么贵，也能看懂 API 账单里 input token 与 output token 为什么要分开定价。

## 2. 概念逐层拆

### Prefill（预填充）

**是什么**：把用户输入的全部 token 一次性送进模型，跑完所有层，产出第一个输出 token。
**为什么需要**：输入已知且完整，可以并行计算，一次矩阵乘就吃下整段 prompt。
**在系统里的位置**：推理的第一阶段，计算密集（compute-bound），决定 TTFT（首 token 延迟）。
**记住这个数**：1,000 token 的输入，单个头的分数矩阵就是 1,000×1,000 ≈ 100 万格；耗时几百毫秒。

### Decode（解码）

**是什么**：每次只送入上一步生成的那一个 token，前向一次，吐出下一个 token。
**为什么需要**：输出是逐 token 生成的，第 n 个 token 依赖第 n−1 个，无法并行。
**在系统里的位置**：推理的第二阶段，访存密集（memory-bound），决定 TPOT（每 token 间隔）。
**记住这个数**：每步几十毫秒，生成 500 个 token 就要循环 500 次。

### KV Cache

**是什么**：把历史 token 在每一层算出的 K 和 V 张量存下来，Decode 时直接复用。
**为什么需要**：K、V 只由该 token 自身与之前的内容决定，算过一次就永远不变，重算是纯浪费。
**在系统里的位置**：跨 step 的运行时状态，存在显存里，形状 `[层数, batch, 头数, 已生成长度, head_dim]`。
**记住这个数**：LLaMA 7B 每 token 0.5MB，4,096 token 就是 2GB。

### Temperature

**是什么**：Softmax 之前把 logits 除以 T，`P(i) = softmax(logit_i / T)`。
**为什么需要**：模型只输出相对大小，需要一个旋钮控制"多敢选低概率词"。
**在系统里的位置**：采样环节，计算后处理，不改变模型权重。
**记住这个数**：T=0.1~0.3 接近确定，T=0.7~0.9 日常对话，T>1.2 明显发散。

### Top-p 与 Top-k

**是什么**：Top-k 只保留概率最高的 k 个；Top-p 从高到低累加，超过 p 就截断。
**为什么需要**：纯按概率采样会偶尔抽到极低概率的怪词，截断能兜住下限。
**在系统里的位置**：采样前的候选集过滤，运行时参数。
**记住这个数**：Top-p 常取 0.9~0.95；累加示例 0.30→0.50→0.65→0.75→0.83→0.88→0.92 在第 7 个截断。

### Continuous Batching

**是什么**：不等整批结束，谁先生成完谁先退出，空出的槽位立刻塞新请求。
**为什么需要**：静态 batch 会被最长的那条拖住，短请求白等，GPU 利用率骤降。
**在系统里的位置**：服务层调度，运行时并发控制，不改模型。
**记住这个数**：8 个请求的批处理耗时接近 1 个，这是吞吐能上去的根本原因。

### 量化（Quantization）

**是什么**：把 float16 权重压到 int8 或 int4，用更低比特存同一批数字。
**为什么需要**：显存带宽是 Decode 的瓶颈，权重越小读得越快，也越装得下。
**在系统里的位置**：部署环节，模型加载前完成，推理时反量化到计算精度。
**记住这个数**：7B 模型 fp16 约 14GB、int8 约 7GB、int4 约 3.5GB。

## 3. 手算推演

**先算单 token 的 KV Cache。** 以 LLaMA 7B 为例：32 层、32 头、每头 128 维、float16（2 字节）。

单个 token 在单层的 K：32 头 × 128 维 = 4,096 个元素。
加上 V：4,096 × 2 = 8,192 个元素。
32 层合计：8,192 × 32 = **262,144 个元素**。
换算字节：262,144 × 2 = **524,288 B = 512 KiB ≈ 0.5 MB**。

交叉验算：每层 K 的 32×128 = 4,096 恰好等于 d_model，所以总量 = 2（K 和 V）× d_model × 层数 = 2 × 4,096 × 32 = 262,144。两条路结果一致。

**再算不同上下文长度。**

4,096 token：524,288 × 4,096 = 2,147,483,648 B = **2 GiB**（原文口径记作 2GB）。
131,072 token（128K）：524,288 × 131,072 = 68,719,476,736 B = **64 GiB**（原文口径记作 64GB）。

比例校验：128K 是 4K 的 32 倍，64 ÷ 2 = 32，线性关系成立。
对比模型本身：7B 参数 fp16 约 14GB。4K 上下文时 cache 只占模型的 1/7；128K 时 cache 是模型的 4.5 倍。**长上下文真正的成本不在权重，在缓存。**

若同时服务 32 个 4K 请求，光 KV Cache 就要 32 × 2 = 64GB，一张 80GB 卡扣除 14GB 权重后已经放不下。

**最后算"有没有 cache"的差距。** 设 prompt 10 个 token，生成 100 个。

无 cache：第 1 步送入 10 个 token，第 2 步 11 个，……，第 100 步 110 个（原文口径）。总处理量 = (10 + 110) × 100 ÷ 2 = **6,000 个 token·次**。
有 cache：Prefill 只做一次 10 个，之后 100 步各 1 个，总计 10 + 100 = **110 个 token·次**。
比值 6,000 ÷ 110 ≈ **54.5 倍**。

严格按"第 i 步处理 9+i 个"算是 10 到 109，累计 5,950，与原文口径差 0.8%，不影响量级结论。

**为什么说一个是 O(n²)、一个是每步 O(n)？**
看投影层：无 cache 时第 i 步要对全部 i 个 token 重算 Q/K/V 与 FFN，单步 O(i)，累计 Σi = **O(N²)**；有 cache 时第 i 步只对 1 个 token 做投影，单步 O(1)，累计 **O(N)**。
再看注意力矩阵：无 cache 时第 i 步要算 i×i 的分数矩阵，单步 O(i²)，累计 **O(N³)**；有 cache 时只有 1 行 Q 去乘 i 个 K，单步 O(i)，累计 **O(N²)**。
以第 100 步为例更直观：无 cache 要重新生成 110 组 K/V、110 行 Q，算出 110×110 的分数矩阵；有 cache 只生成 1 组 K/V、1 行 Q，与缓存里已有的 110 组 K/V 做 1×110 的点积。**参与的 K/V 数量都是 110，但被乘的 Q 从 110 行降到 1 行——省掉的是重复计算，不是历史本身。**
两层口径不同，但结论一致：cache 把"每一步都随长度变重"变成"每一步只随长度线性变重"，而投影这部分彻底变成常数。

## 4. 代码逐行

`inference.py`，依赖 transformers 与 torch，用 GPT-2 对比两种写法。

```python
outputs = model(generated)
next_logits = outputs.logits[0, -1, :]
```
无 cache 版本。`generated` 每一步都在变长，整段重新前向，只取最后一个位置的 logits。打印里能看到"处理了 N 个 token"，N 随 step 递增。

```python
outputs = model(input_ids, use_cache=True)
```
第一次调用是 Prefill：送入全部 prompt，同时让模型返回 `past_key_values`。这一步最慢，因为要处理整段输入。

```python
outputs = model(next_token_ids, past_key_values=past_kv, use_cache=True)
past_kv = outputs.past_key_values
```
Decode 分支：只送 1 个 token，把上一步的缓存传进去，模型内部把新 K/V 追加到旧缓存尾部。`next_token_ids` 形状是 `[1, 1]`，这就是"每步只处理一个"的字面实现。

```python
cache_elements = sum(
    past_kv[l][0].numel() + past_kv[l][1].numel()
    for l in range(n_layers)
)
cache_bytes = cache_elements * 4  # float32
```
逐层累加 K 与 V 的元素个数。脚本按 float32 算（每元素 4 字节），所以 GPT-2 实测值会比按 fp16 手算的大一倍；换成 float16 就把 4 改成 2。

```python
speedup = no_cache_total / cache_total if cache_total > 0 else 0
```
总耗时相除得到加速比。原文实测的逐步数据是：无 cache 从 15ms 涨到 35ms，有 cache 的 Prefill 18ms、之后稳定 4ms。

```python
logits = logits / temperature
logits = top_p_filter(logits, p=0.9)
probs = softmax(logits)
next_token = sample(probs)
```
采样四步：先调温度改变分布陡峭度，再截断候选集，再归一化，最后按概率抽一个。顺序不能反，先截断再调温度会改变候选集大小。

## 6. 类比拆解

| 原文类比 | 它映射到哪一步 | 这个比喻在哪儿会失效 |
|---|---|---|
| 打字机效果 | Decode 逐 token 输出 | 打字机是机械匀速，Decode 受显存带宽与批内排队影响，快慢会抖 |
| 把历史 K/V 存起来查 | KV Cache | 查表是只读，Cache 每步还要追加写入，长度增长会拖慢访存 |
| 一口气读完题目再答题 | Prefill | 人读题可以回看，Prefill 是单向一次前向，且受因果掩码限制 |
| 几百万人在同一秒提问，排队 | 请求队列 | 真实系统用 Continuous Batching，不是先来先服务的一条队列，短请求可以插队 |
| 把 8 个请求打包一起算 | Batching | 打包会拉高单请求延迟，显存也被 8 份 KV Cache 同时占用，不是免费的 |
| 把参数从 16 位压到 8 位 | 量化 | 压缩会掉精度，数学与代码任务对量化误差比闲聊敏感得多 |

## 7. 五个误区

❌ 模型是先想好整段回答再输出 → ✅ 自回归，一次只前向一个 token，循环几百次 → 因为第 n 个 token 的输入包含第 n−1 个 token，没生成出来就无法计算下一个。

❌ 流式输出是前端做的打字动画 → ✅ 那就是真实解码速度，字是一个一个算出来的 → 因为服务端每算完一个 token 就立刻推一个 SSE 分片，前端只是照收。

❌ 有了 KV Cache 就能无限长上下文 → ✅ Cache 省的是重复计算，不省显存，显存随长度线性增长 → 因为每个历史 token 的 K/V 都得留着，128K 就要 64GB，比模型还大。

❌ Temperature 越大模型越聪明 → ✅ 它只改变采样随机性，不改变模型的知识与能力 → 因为温度只在 softmax 前做除法，logits 的相对排序完全没变，只是被压平或拉尖。

❌ 批处理会让每个请求都更快 → ✅ 吞吐上升，单请求延迟通常变高 → 因为多个序列共享一次前向，GPU 利用率提高，但排队与显存争用会让单个用户等更久。

## 9. 自测 8 题（含答案要点）

1. Prefill 和 Decode 的本质区别是什么？
   要点：Prefill 一次并行处理全部输入，是 compute-bound；Decode 每步只处理 1 个 token，是 memory-bound。

2. 为什么 K 和 V 能缓存，Q 不能？
   要点：K、V 只依赖该 token 及其之前的内容，生成后不再变化；Q 属于当前新 token，每步都不同。

3. KV Cache 省掉的具体是哪部分计算？
   要点：历史 token 的 Q/K/V 投影、FFN 前向、以及完整的注意力分数矩阵，全部不再重算，只算新 token 并追加 K/V。

4. Top-k 与 Top-p 的核心差别？
   要点：k 固定，候选数不随分布变化；p 自适应，模型确定时候选少、不确定时候选多。

5. Continuous Batching 解决了什么问题？
   要点：静态 batch 要等最长序列结束；连续批处理让完成的请求立刻退出、新请求立刻进入，提升 GPU 利用率。

6. 为什么长上下文特别吃显存？
   要点：权重是常数，KV Cache 随 token 数线性增长；128K 时缓存可达 64GB，是 7B 模型权重的 4.5 倍。

7. 【计算】一个 13B 模型，40 层、40 头、head_dim=128、float16，单 token 的 KV Cache 是多少？8K 上下文呢？
   要点：40×40×128=204,800 元素/层；×2(K,V)=409,600；×2 字节=819,200B≈0.78MB；8,192 token → 819,200×8,192=6,710,886,400B=6.25GiB。

8. 【计算】prompt 10 token、生成 100 token，无 cache 与有 cache 各处理多少 token·次？比值多少？
   要点：无 cache 为 (10+110)×100/2=6,000；有 cache 为 10+100=110；比值约 54.5 倍。

## 10. 一页速记

- 推理分两段：Prefill 并行吃输入，Decode 串行吐输出。
- 第一个字慢，是因为整段 prompt 都要跑完 32 层。
- 后面快，是因为每步只算 1 个 token。
- KV Cache 缓存的是历史 token 的 K 与 V，不是 Q。
- 每步仍要和全部历史做注意力，只是不再重算它们的投影。
- 时间省下来了，显存花出去了，这是纯粹的以空间换时间。
- 7B 模型每 token 0.5MB，4K 要 2GB，128K 要 64GB。
- 温度调分布的陡峭度，Top-p 调候选集的大小，两者作用不同。
- 批处理提高吞吐，通常牺牲单请求延迟。
- 量化压的是权重，压不了 KV Cache 的长度增长。

三个关键数字：**0.5MB**（7B 每 token 的 KV Cache）、**54.5×**（100 步生成的 token·次比值）、**64GiB**（128K 上下文的缓存）。
