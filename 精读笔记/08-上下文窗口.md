# 第 8 篇精读｜上下文窗口——大模型的"工作记忆"到底有多大？

> 原文：llm-08-context-window.md ｜ 前置：第 7 篇 ｜ 核心一句话：窗口是"输入 + 输出"的共享上限，被 n² 计算量与线性 KV Cache 双重锁死。

## 0. 三句话抓住它

- 窗口是硬上限，输入和输出共享同一份额度。
- 长度翻倍，Attention 计算量翻四倍，KV Cache 只翻一倍。
- 装得下不等于读得懂，中间位置的信息最容易被漏掉。

## 1. 这一篇在补哪个洞

第七篇结尾留了三个问题：为什么模型不能记住无限长的文本、128K 到底是什么意思、位置编码怎么区分第 1 个词和第 10 万个词。第七篇还留了一笔没算完的账——它为 Decode 引入了 KV Cache，但只算了"每步省下多少重算"，没算"上下文变长后这笔缓存会涨成什么样"。

这一篇把账算完。KV Cache 不是常数，它随 n 线性增长；Attention 更狠，随 n² 增长。于是"窗口能开多大"从产品参数问题，变成了显存与算力的物理问题。

补上的洞是视角切换：前七篇把模型当成一个定长函数，这一篇第一次让"输入长度"成为变量——而所有成本都对它非线性敏感。

还要看清一件事：原文列了三个瓶颈，真正被解决的只有第三个。RoPE 拆掉了位置编码的页数限制，但 n² 和 KV Cache 一条都没消失。所以"窗口从 1K 涨到 1M"不是模型变强了 1000 倍，而是工程上愿意为同样的注意力多付 95 万倍算力和 977 倍显存。

## 2. 概念逐层拆

### 上下文窗口

- **是什么**：一次前向能看到的 token 总数上限，输入 token + 输出 token ≤ 上限。
- **为什么需要**：Attention 要两两比较，位置编码要有位置可用，KV Cache 要有地方放。
- **在系统里的位置**：推理层之上的调度约束——超了不是变慢，是报错或被截断。
- **记住这个数**：GPT-2 = 1,024；GPT-4o = 128,000；2026 旗舰 = 1,000,000。

### n² 的 Attention

- **是什么**：n 个 token 每个都要和 n 个 token 算相关度，分数矩阵是 n×n。
- **为什么需要**：这是"理解上下文"的代价，第四篇的 Q·Kᵀ 就是这张矩阵。
- **在系统里的位置**：Prefill 阶段的主要算力开销，随长度平方上涨。
- **记住这个数**：128K（131,072）时约 1.72×10¹⁰ 个分数。

### KV Cache

- **是什么**：缓存历史 token 的 K、V，Decode 时不再重算。
- **为什么需要**：没有它，每生成一个 token 都要重跑全部历史，第七篇的加速就没了。
- **在系统里的位置**：显存里的常驻数组，和模型权重抢同一张卡。
- **记住这个数**：7B 配置下每 token 512 KiB；128K 要 64 GiB。

### 绝对位置编码表

- **是什么**：一张 max_len × d_model 的可学习表，GPT-2 是 1024×768。
- **为什么需要**：Embedding 不含顺序，"狗咬人"和"人咬狗"的向量是一样的。
- **在系统里的位置**：Embedding 层，与 token 向量逐元素相加。
- **记住这个数**：1024 行；第 1025 个 token 无表可查，直接 IndexError。

### RoPE

- **是什么**：按位置给 Q/K 乘旋转矩阵，用角度差表示相对距离。
- **为什么需要**：查表法把窗口写死，RoPE 用公式算，位置 10 万也能算。
- **在系统里的位置**：Attention 内部，只作用在 Q、K 上，不作用于 V。
- **记住这个数**：base = 10000，不同维度对用不同频率。

### Lost in the Middle

- **是什么**：长上下文中开头与结尾召回高、中间低，呈 U 形曲线。
- **为什么需要**：解释"标称 128K、实际效果打折"。
- **在系统里的位置**：不是架构约束，是训练分布与注意力稀释的联合结果。
- **记住这个数**：关键指令放头尾，别放正中间。

### 长上下文的三种减法

- **是什么**：上下文压缩（把历史摘要成短文）、滑动窗口（每个 token 只连最近 W 个）、稀疏注意力（少量锚点全连接、其余只看附近）。
- **为什么需要**：n² 和 n 都太贵，只能减少"被比较的对数"。
- **在系统里的位置**：压缩在应用层做，另外两个在注意力实现里做，模型结构直接决定。
- **记住这个数**：W 常取 4096 或 8192；一次摘要常见 10,000 字压到 500 字。

## 3. 手算推演

### 3.1 每 token 的 KV 成本

原文公式：`n × 层数 × 头数 × 每头维度 × 2(K和V) × 2字节`。

7B 配置（32 层 / 32 头 / 128 维 / fp16）：

```
32 × 32 × 128 × 2 × 2 = 524,288 字节 = 512 KiB = 0.5 MiB / token
```

### 3.2 五档长度对照

| 长度 | n | Attention 分数 n² | 计算量（相对成本） | KV Cache | KV 倍数 |
|---|---|---|---|---|---|
| 1K | 1,024 | 1.05×10⁶ | 1× | 0.5 GiB | 1× |
| 4K | 4,096 | 1.68×10⁷ | 16× | 2 GiB | 4× |
| 32K | 32,768 | 1.07×10⁹ | 1,024× | 16 GiB | 32× |
| 128K | 131,072 | 1.72×10¹⁰ | 16,384× | 64 GiB | 128× |
| 1M | 1,000,000 | 1.00×10¹² | 953,674× | 488 GiB | 977× |

相对成本按 Prefill 的 Attention 计算量计（长上下文时它主导）；KV 单独列一列，因为它是显存而不是算力。

逐行验算两格：32K 是 32,768 × 512 KiB = 16,777,216 KiB = 16 GiB；1M 是 1,000,000 × 512 KiB = 512,000,000 KiB = 488.28 GiB。可以看到 KV 列每一格都只是"token 数 × 512 KiB"，没有任何隐藏系数。

1M 这一行按代码里的 1,000,000 记。若按 2²⁰ = 1,048,576 记，KV 是 512 GiB、Attention 倍数是 1,048,576×——差 4.9%，不影响任何结论，但引用时要说明用的是哪种"兆"。

换算成字节更直观：0.5 GiB = 536,870,912 B；2 GiB = 2,147,483,648 B；16 GiB = 17,179,869,184 B；64 GiB = 68,719,476,736 B；488.28 GiB = 524,288,000,000 B。五档都等于 `n × 524,288`。

原文口径：按 128K = 128,000 记，n² = 16,384M ≈ 1.64×10¹⁰，与本表 131,072 的结果差 4.8%。原文写的"64 GB"其实是 64 GiB（131,072 × 512 KiB = 68,719,476,736 B），说成 GB 是口语化处理。两个口径都保留，但同一行里别混用。

### 3.3 n 翻倍时各列涨几倍

- Attention 分数：(2n)² / n² = **4 倍**。
- KV Cache：2n / n = **2 倍**。
- 相对成本：**4 倍**；但摊到每个 token 上只有 **2 倍**。
- 1K → 1M：长度 ×977，算力 ×95.4 万，显存 ×977。

为什么显存不是平方：KV 是"每个 token 存一份固定大小的 K/V"，历史只追加不重复；Attention 是"新 token 和全部历史比一遍"，每个新 token 都要重扫全场。一个是仓库面积，一个是每次盘点的工时。

### 3.4 一张卡装得下吗

按原文口径 14 GB 权重 + 64 GB KV = 78 GB，看似塞得进 80 GB A100。但 64 实际是 64 GiB = 68.7 GB，仅这两项就 82.7 GB，已经溢出；再加激活值、CUDA context 和碎片，单卡跑 128K 基本不可行。1M 的 488 GiB 更需要 7 张 80 GB 卡只放 cache（488 ÷ 80 = 6.1，按 GB 算 6.6），权重还没算。厂商标的窗口是"能跑通一次"的实验室值，不是"能稳定服务"的部署值。

## 6. 类比拆解

| 原文类比 | 映射到哪一步 | 这个比喻在哪儿会失效 |
|---|---|---|
| 一次性工作台 | 窗口总容量 | 工作台摆满还能挤一挤，token 超一个就直接截断或报错，没有"挤"的余地 |
| 身份证只印 1024 张 | 绝对位置编码表 | 身份证能补办，wpe 是训练好的参数，补一行等于重新训练 |
| 时钟指针 | RoPE 的相对距离 | 时钟转一圈会重合，RoPE 靠多频率降低混叠，但远距离精度仍会下降 |
| 同时处理 3 件事 vs 300 件事 | 有效上下文衰减 | 人可以分批处理，模型的单次前向不能"分批再汇总" |
| U 形曲线 | Lost in the Middle | U 形是统计趋势不是硬规则，短窗口时几乎观察不到 |
| 上下文是"咽喉" | 模型与外部世界的接口 | 咽喉只限制通过量，窗口还决定"能不能看见"，看不见的内容连被限流的资格都没有 |

## 7. 五个误区

- ❌ 128K 窗口就能输出 128K → ✅ 输入 + 输出共享 128K → 因为上限是总和，塞满输入就没地方生成。
- ❌ 窗口越大长文理解越好 → ✅ 有效长度小于标称长度 → 因为中间信息被稀释，落在 U 形谷底。
- ❌ RoPE 能无限外推 → ✅ 公式能算，但分布没训过 → 因为超出训练长度后角度组合陌生，需要 NTK/YaRN 调参或继续训练。
- ❌ KV Cache 只和模型大小有关 → ✅ 还和 n 线性相关 → 因为每个 token 每层每头都要存一份 K、V。
- ❌ 聊久了模型"忘了" → ✅ 是最早的 token 被截掉 → 因为窗口外的东西根本没进前向，不是记忆衰退。

## 9. 自测 8 题（含答案要点）

**概念题**

1. 窗口上限包不包括输出？——包括，输入 + 输出 ≤ 上限。
2. 为什么 GPT-2 超过 1024 会崩？——wpe 只有 1024 行，位置索引越界。
3. RoPE 为什么不怕位置 100,000？——公式计算而非查表，且只用相对角度差。
4. KV Cache 为什么和 n 成正比？——每个 token 每层每头都要存 K、V，单位成本固定。
5. Lost in the Middle 的工程含义？——关键指令放头尾，别埋在中间。
6. 滑动窗口注意力的代价？——O(nW) 省算力，但超出 W 的远距离依赖直接看不见。

**计算题**

7. LLaMA 70B：80 层、64 头、head_dim 128、fp16，32K 上下文的 KV 多大？
   每 token = 80×64×128×2×2 = 2,621,440 B = 2.5 MiB；×32,768 = **80 GiB**。

8. 7B 模型（权重 14 GB）放 80 GB A100，只留 KV，理论最长多少 token？
   (80−14) = 66 GiB = 69,206,016 KiB；÷512 KiB = **135,168 token ≈ 135K**。

## 10. 一页速记

- 窗口 = 输入 + 输出，共享一份额度。
- n² 管算力，n 管显存，两个瓶颈分开记。
- 每 token KV = 层 × 头 × d × 4 字节。
- 7B 每 token 0.5 MiB，128K 就是 64 GiB。
- 1K→1M，算力涨 95 万倍，显存只涨 977 倍。
- RoPE 用旋转角度差表示相对位置。
- 位置编码不再是瓶颈，算力和显存才是。
- 中间信息最容易被漏，指令放两头。
- 窗口满了是截断，不是遗忘。
- 压缩、滑动窗口、稀疏注意力是三套减法。

三个关键数字：**1,024** / **512 KiB** / **64 GiB**。
