# 第 10 篇精读｜从大模型到 Agent——下一个词预测如何长出手脚

> 原文：llm-10-agent.md ｜ 前置：第 9 篇 ｜ 核心一句话：Agent = 普通 LLM + 工具 + 一个循环，模型只负责"想"，代码负责"做"。

## 0. 三句话抓住它

- Agent 不是新模型，是 LLM 外套了一层工具与循环。
- Function Calling 的本质，是模型生成一段特定格式的 JSON。
- 模型无状态，每一步都要把全部历史重新发一遍。

## 1. 这一篇在补哪个洞

第九篇把"为什么要堆算力"解释清楚了，但堆出来的模型仍然只会一件事：输出 token。它不知道今天天气，也打不开一个文件。第九篇结尾把这个矛盾交给收官篇：一个只会预测下一个词的函数，怎么变成能查天气、读文件、跑命令的 Agent？

答案不在模型内部。模型没有长出任何新器官，变的是外面包的那一层——一份工具说明书、一个 JSON 协议、一个 while 循环。这一篇补的洞就是"从文本到行动"的这段胶水，而且这段胶水只有几十行。

它同时回收了前九篇的全部伏笔：分词、Embedding、Attention、训练、推理、上下文窗口、Scaling Law，最后全部落在同一次 `chat.completions.create()` 里。看懂这一篇，你就知道 Agent 的能力边界，其实就是大模型的能力边界加循环的工程边界。

## 2. 概念逐层拆

### Function Calling

- **是什么**：模型生成一段 JSON，声明"要调哪个工具、传什么参数"，它自己不执行任何函数。
- **为什么需要**：纯文本碰不到外部世界，JSON 是可被外部代码解析的行动意图。
- **在系统里的位置**：模型输出与真实执行之间的协议层，跨过去就出了模型。
- **记住这个数**：模型内部执行的函数调用是 0 个；它只产出 token。

### tools schema

- **是什么**：随每次请求发送的 JSON Schema，描述工具名、用途、参数类型。
- **为什么需要**：模型靠它知道"有哪些工具可用、参数怎么填"。
- **在系统里的位置**：系统提示的一部分，占上下文，而且每轮都重发。
- **记住这个数**：本篇 3 个工具约 180 token，3 轮就是 540 token。

### Agent 循环

- **是什么**：LLM 预测 → 有 tool_calls 就执行并回填 → 再预测，直到输出纯文本。
- **为什么需要**：一次预测只能走一步，多步任务需要状态机来推进。
- **在系统里的位置**：模型之外的编排层，核心逻辑 20–50 行就够。
- **记住这个数**：`max_steps=10`，这是防死循环的硬闸。

### messages 状态

- **是什么**：唯一的跨步记忆，包含 system / user / assistant / tool 四类消息。
- **为什么需要**：模型本身无状态，每一步都要把完整历史重发给它。
- **在系统里的位置**：客户端持有，服务端每次重新 Prefill 一遍。
- **记住这个数**：上下文长度 = 所有消息 token 之和 + tools schema。

### tool_call_id

- **是什么**：assistant 的每个 tool_call 与 tool 结果的配对键。
- **为什么需要**：并行多工具时，靠 id 把结果对回对应的调用。
- **在系统里的位置**：消息协议层，缺一个就返回 400。
- **记住这个数**：1 个 call → 1 个 id → 1 条 tool 消息，缺一不可。

### 错误累积

- **是什么**：第 k 步的采样错误，会成为第 k+1 步的输入事实。
- **为什么需要**：解释 Agent 为什么越走越偏，而不是"平均而言还行"。
- **在系统里的位置**：循环的复利效应，步数越多越明显。
- **记住这个数**：单步 95% 正确，10 步全对只有 0.95¹⁰ ≈ 60%。

## 3. 手算推演

场景：**"统计当前目录下 .py 文件的数量，并把数字写进 report.txt"**。

计数规则（经验估算，±10%）：1 个汉字 ≈ 1 token；4 个 ASCII 字符 ≈ 1 token；JSON 结构符号每个 ≈ 1 token；tools schema 3 个工具 ≈ 180 token。绝对值有误差，但每步的增量与占比可以照着表复算。

### Step 1：模型决定先数文件

输入：

```python
messages = [
  {"role": "system", "content": "你是一个能使用工具的助手，回答要简洁。"},   # 20
  {"role": "user",   "content": "统计当前目录下 .py 文件的数量，并把数字写进 report.txt"},  # 29
]
# tools schema 180 tokens（不在 messages 里，但占上下文、也计费）
# 本次输入 = 180 + 20 + 29 = 229 tokens
```

模型输出（45 token）：

```python
{"role": "assistant", "content": None,
 "tool_calls": [{"id": "call_1", "type": "function",
   "function": {"name": "execute_bash",
                "arguments": "{\"command\": \"ls *.py | wc -l\"}"}}]}
```

### Step 2：代码执行，结果回填

```python
{"role": "tool", "tool_call_id": "call_1", "content": "12"}   # 15 token
# 本次输入 = 229 + 45 + 15 = 289 tokens
```

模型看到 "12"，输出第二个调用（35 token）：

```python
{"role": "assistant", "content": None,
 "tool_calls": [{"id": "call_2", "type": "function",
   "function": {"name": "write_file",
                "arguments": "{\"path\": \"report.txt\", \"content\": \"12\"}"}}]}
```

### Step 3：写入成功，模型收尾

```python
{"role": "tool", "tool_call_id": "call_2", "content": "已成功写入 report.txt"}   # 15 token
# 本次输入 = 289 + 35 + 15 = 339 tokens

{"role": "assistant", "content": "当前目录共有 12 个 .py 文件，已写入 report.txt。"}   # 28 token
# 没有 tool_calls → 循环结束
```

### 3.1 上下文与计费逐轮增长

| 步 | 新增内容 | 新增 token | 本次输入 | 本次输出 | 累计计费 |
|---|---|---|---|---|---|
| 1 | system 20 + user 29 + tools 180 | 229 | 229 | 45 | 274 |
| 2 | assistant 45 + tool 15 | 60 | 289 | 35 | 598 |
| 3 | assistant 35 + tool 15 | 50 | 339 | 28 | 965 |

三个结论：

1. 输入从 229 涨到 339，只有 1.48 倍，但任务才走了 3 步；步数一多，这条曲线是线性上升的。
2. tools 的 180 token 被计费 3 次，共 540，占 965 的 **56%**——短任务里，固定开销比任务本身还贵。
3. 第 3 步的 339 里，有 289 是第 2 步已经发过的。**同一段历史被重复计费**，这是 Agent 比聊天贵得多的直接原因。

如果 `ls` 返回的不是 "12" 而是 3,000 token 的日志：第 2 步输入变成 229+45+3,000 = 3,274，第 3 步变成 3,324，总输入 6,827，是原来的 **8 倍**。工具输出有多长，Agent 的账单就有多陡。

## 4. 代码逐行

文件 `tiny_agent.py`，约 50 行核心逻辑。

```python
client = OpenAI(
    api_key=os.environ.get("OPENAI_API_KEY", "sk-xxx"),
    base_url=os.environ.get("OPENAI_BASE_URL", "https://api.openai.com/v1"),
)
```

在干什么：把客户端指向任意兼容 OpenAI 协议的服务。跑出来：只改环境变量就能从 GPT-4o-mini 切到 Qwen、DeepSeek，代码一行不动。

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "execute_bash",
            "description": "Execute a bash command on the system",
```

在干什么：声明工具（节选，后面还有 parameters 和另外两个工具，共 3 个）。跑出来：这段 JSON 每轮都随请求发出，模型"读"到它才知道自己能做什么；代价是约 180 token 的固定上下文税。

```python
messages.append(assistant_msg)
```

在干什么：把模型这一轮的回复（含 `tool_calls`）原样写回历史。跑出来：不回填就 400——因为下一条 tool 消息必须紧跟在一条带 tool_calls 的 assistant 消息后面。

```python
for tool_call in assistant_msg.tool_calls:
    func_args = json.loads(tool_call.function.arguments)
```

在干什么：遍历本轮所有调用，把 arguments 字符串解析成 dict。跑出来：模型一次可以要求调多个工具；arguments 是字符串，JSON 解析失败要当异常处理。

```python
result = available_tools[func_name](**func_args)
```

在干什么：按工具名在白名单字典里分发。跑出来：不在字典里就返回"未知工具"，不会执行任意代码——白名单挡的是函数名，不挡命令内容。

```python
messages.append(
    {
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": result,
    }
)
```

在干什么：把执行结果回填，并用 id 配对。跑出来：下一轮模型能看到 "12" 或 "已成功写入 report.txt"。

```python
display = result[:200] + "..." if len(result) > 200 else result
```

在干什么：只截断终端打印。跑出来：屏幕只显示 200 字，但 `content` 里是全文——上下文照样被吃满。这是最容易误判的一行。

```python
for step in range(max_steps):
```

在干什么：10 步硬闸。跑出来：模型如果不肯收尾，循环到 10 就停，返回"达到最大步数"。

安全提醒：`subprocess.run(command, shell=True)` 意味着模型生成的任意命令都会被执行。工具名是白名单，命令不是。读到一段恶意文件内容，就可能被诱导执行 `rm`。真实系统必须加权限 Hook、目录白名单和人工确认。

| 量 | 值 | 含义/出处 |
|---|---|---|
| 工具数 | 3 | execute_bash / read_file / write_file |
| tools schema | ≈180 token | 本篇估算，每轮重发 |

| 3 步总输入 | 857 token | 229+289+339 |
| 3 步总输出 | 108 token | 45+35+28 |

| 固定开销占比 | 56.0% | 540/965 |
| 上下文增长 | 1.48× | 339/229 |
| 单任务调用次数 | 5–10 次 | 原文第九篇 |

## 6. 类比拆解

| 原文类比 | 映射到哪一步 | 这个比喻在哪儿会失效 |
|---|---|---|
| 大脑 + 四肢 | LLM + 工具 | 四肢有本体感觉，Agent 只能靠文本结果间接判断成败，动作是否真的生效要靠外部校验 |
| 工具说明书 | tools schema | 看得懂不等于会用；schema 越长、工具越多，选错的概率反而上升 |
| "和 Thank you very → much 完全一样的机制：统计规律" | 模型学会输出 JSON | 统计规律能保证格式像，不保证语义对——模型可以流畅地生成一个参数完全错误的调用 |
| 外面包的那一层 | Agent 编排层 | 这层"包装"会改变系统行为与成本，不是透明装饰；包装错了，模型再强也没用 |
| 模型做"决策"，代码做"执行" | Function Calling 的职责边界 | 一旦工具内部再调 LLM，决策与执行的边界就糊了，出错后也很难归因 |

## 7. 五个误区

- ❌ Agent 是一种新型 AI → ✅ 普通 LLM + 工具 + 循环 → 因为模型权重没变，变的是外面的调用协议。
- ❌ Function Calling 是模型在内部执行函数 → ✅ 它只生成 JSON → 因为 Transformer 输出的是 token 概率，没有系统调用能力。
- ❌ 工具越多 Agent 越强 → ✅ schema 占上下文、选择空间变大 → 因为候选越多，prompt 越长，选错的概率也越高。
- ❌ 多轮对话模型"记得"之前 → ✅ 每轮都把 messages 重发 → 因为模型无状态，窗口外的东西等于不存在。
- ❌ Agent 出错是模型不够大 → ✅ 采样 + 错误累积 + 缺校验 → 因为每步都是概率输出，第 3 步的错会成为第 4 步的前提。

## 9. 自测 8 题（含答案要点）

**概念题**

1. Agent 的三要素？——LLM、工具、循环。
2. 模型"调用"工具时实际做了什么？——生成一段声明工具名与参数的 JSON。
3. 为什么必须回填 assistant 消息？——tool 结果必须对应一条带 tool_calls 的 assistant 消息，否则协议不成立。
4. messages 为什么是唯一记忆？——模型无状态，每次请求都靠它重建上下文。
5. 为什么 tools schema 也占上下文？——它随每次请求一起发送，不是免费的系统提示。
6. 单步 90% 正确，5 步全对概率？——0.9⁵ = 0.590 ≈ 59%。

**计算题**

7. 按第 3 节轨迹，求总输入、总输出、总 token、tools 占比。
   输入 229+289+339 = **857**；输出 45+35+28 = **108**；总计 **965**；tools 540/965 = **56.0%**。

8. 20 步任务，初始 2,000 token，每步净增 1,500 token，求总输入与最终上下文。
   总输入 = Σ(2000+1500k)，k=0…19 = 20×2000 + 1500×190 = 40,000+285,000 = **325,000 token**；
   最终上下文 = 2000+1500×19 = **30,500 token**。
   账单是 32.5 万，但任何一次请求都没超过 3.05 万——**累计计费 ≠ 单次窗口占用**。

## 10. 一页速记

- Agent = LLM + 工具 + 循环，没有新模型。
- Function Calling = 生成 JSON，不是执行。
- tools schema 每轮重发，是固定上下文税。
- messages 是唯一记忆，模型本身无状态。
- 一个 tool_call 必须配一个 tool_call_id。
- 终止条件：模型输出不带 tool_calls 的纯文本。
- 每步都是一次完整 Prefill，历史越长越慢。
- 错误会复利，步数越多越危险。
- 工具输出是上下文膨胀的主因。
- 显示截断不等于上下文截断。
- 分级调用：小模型决策，大模型推理。
- 白名单挡函数名，不挡命令内容。

三个关键数字：**3 个工具** / **965 token** / **10 步上限**。
