# 第 13 篇精读｜Token 计费：为什么输出比输入贵

> 原文：llm-13-token-pricing.md ｜ 前置：第 12 篇 ｜ 核心一句话：价目表不是商业策略，而是 Prefill 与 Decode 两种资源消耗方式的直接折算。

## 0. 三句话抓住它

- 按 token 收费，因为计算量只与 token 数成正比。
- 输出贵，因为 Decode 串行，每个 token 都要重读一遍权重。
- 缓存便宜，因为命中的前缀跳过了整段 Prefill 计算。

## 1. 这一篇在补哪个洞

第 2 篇讲了 token 是什么、中英文效率差多少，但停在“分词”层面；第 7 篇讲了 Prefill 与 Decode 的流程，但没算钱；第 12 篇讲了带宽决定 decode 速度，但没折成单价。三块知识各自成立，却没人把它们拼成一张账单。这篇番外就干这件事：把第 7 篇的两个阶段、第 12 篇的带宽瓶颈，映射成输入价、输出价、缓存价三行数字。

要补的现实问题很具体：同样一次调用，为什么贴一万字和说“你好”价格差几百倍；为什么输出单价是输入的 2 倍；为什么 Agent 场景反复调用同一个 System Prompt 会便宜 12 倍；为什么改一个字，缓存优惠全部消失。这些都不是定价玄学，而是 KV Cache 的物理后果。

读完要达到的标准：拿到 usage 里的三个数字（缓存命中、缓存未命中、输出），能在一分钟内算出准确账单，并判断该优化哪一项。原文全部采用 DeepSeek V4 的定价，本篇不替换模型。

## 2. 概念逐层拆

### 2.1 Token 作为计量单位

**是什么**：模型实际处理的离散符号，文本经 BPE 分词后得到，中文一个字可能对应 1–2 个 token，英文一个词可能对应 1–多个 token。

**为什么需要**：计算量与 token 数成正比，与字数、调用次数都不成正比；按次收费会让长文请求亏本，按字收费会让中英文成本错位。

**在系统里的位置**：它是唯一同时贯穿 Embedding、Attention、KV Cache 和账单的量。

**记住这个数**：1000 个 token 就是跑 1000 步 Transformer，不管它是 500 个英文词还是 600 个汉字。

### 2.2 Prefill（输入阶段）

**是什么**：所有输入 token 一次性送入模型，并行做完整的 Q/K/V 投影、Attention 和 FFN。

**为什么需要**：只有把上下文编码完，模型才知道生成第一个 token 时该关注什么。

**在系统里的位置**：对应输入计价；它的产出是每层的 K 和 V，也就是后续可被复用的缓存。

**记住这个数**：1000 个输入 token 在 7B 模型上约 50ms，GPU 利用率约 80%（原文口径）。

### 2.3 Decode（输出阶段）

**是什么**：每次只生成一个 token，把它接到序列尾部，再跑一遍全部层。

**为什么需要**：自回归生成的本质决定了不能并行——第 n+1 个 token 依赖第 n 个。

**在系统里的位置**：对应输出计价；它是整条链上 GPU 利用率最低的环节。

**记住这个数**：同样 1000 个 token，Decode 约 5,000–10,000ms，是 Prefill 的 100 倍（原文口径）。

### 2.4 前缀缓存（Prefix Cache）

**是什么**：把已经算过的前缀在每层的 K/V 存下来，下次请求命中相同前缀时直接复用，跳过 Prefill。

**为什么需要**：System Prompt、工具定义、长文档在多轮调用中高度重复，重算纯属浪费。

**在系统里的位置**：位于 Prefill 之前的一道查表；命中则整段跳过 Transformer，未命中才走完整计算。

**记住这个数**：只对“从头开始的连续相同前缀”有效，第一个不同的 token 之后全部失效。

### 2.5 缓存命中价

**是什么**：命中部分的输入单价。V4-Pro 为 1 元/百万 token，V4-Flash 为 0.2 元。

**为什么需要**：命中部分只花存储和读取成本，不花算力，价格必须单独列。

**在系统里的位置**：账单的第一行，也是 Agent 场景最值得优化的一行。

**记住这个数**：V4-Pro 命中 1 元 vs 未命中 12 元，相差 12 倍。

### 2.6 混合单价（Blended Price）

**是什么**：总费用除以总 token 数，得到这次请求的实际平均单价。

**为什么需要**：价目表有三行，无法直接比较不同请求结构的贵贱；混合单价可以横向比。

**在系统里的位置**：成本归因和容量规划用的派生指标，不在官方价目表里。

**记住这个数**：原文示例的 2800 个 token 总费用 0.0267 元，混合单价 9.54 元/百万。

### 2.7 Agent 成本放大

**是什么**：Agent 每一步都是一次独立调用，且上下文随步数累积，输入 token 逐步变长。

**为什么需要**：单轮对话的成本直觉在 Agent 上完全失效。

**在系统里的位置**：第 10 篇 Agent 循环的直接成本后果，也是前缀缓存最大的受益场景。

**记住这个数**：原文口径，10 步 Agent 的总 token 消耗可能是单轮对话的 20–50 倍。

## 3. 手算推演

**设定**：输入 2000 token，其中 1500 命中缓存、500 新增；输出 800 token。V4-Pro 单价：命中 1、未命中 12、输出 24（元/百万 token）。

**第一笔：缓存命中部分。** 1500 ÷ 1,000,000 × 1 = **0.0015 元**。

**第二笔：缓存未命中部分。** 500 ÷ 1,000,000 × 12 = **0.0060 元**。

**第三笔：输出部分。** 800 ÷ 1,000,000 × 24 = **0.0192 元**。

**合计**：0.0015 + 0.0060 + 0.0192 = **0.0267 元**，与原文一致。

| 项目 | token | 单价（元/M） | 费用（元） | 占总费用 |
|---|---|---|---|---|
| 缓存命中 | 1500 | 1 | 0.0015 | 5.6% |
| 缓存未命中 | 500 | 12 | 0.0060 | 22.5% |
| 输出 | 800 | 24 | 0.0192 | 71.9% |
| 合计 | 2800 | — | 0.0267 | 100% |

**占比校验**：输出 token 只占总量的 800÷2800 = **28.6%**，却占了 **71.9%** 的费用，原文“29% 的 token、72% 的费用”成立。混合单价 = 0.0267 ÷ 2800 × 1,000,000 = **9.54 元/百万**。

**换 V4-Flash（0.2 / 1 / 2）再算一遍。**

- 命中：1500 ÷ 1e6 × 0.2 = **0.0003 元**
- 未命中：500 ÷ 1e6 × 1 = **0.0005 元**
- 输出：800 ÷ 1e6 × 2 = **0.0016 元**
- 合计 **0.0024 元**；混合单价 0.857 元/百万。

| 项目 | Pro 费用 | Flash 费用 | Flash 占比 |
|---|---|---|---|
| 命中 | 0.0015 | 0.0003 | 12.5% |
| 未命中 | 0.0060 | 0.0005 | 20.8% |
| 输出 | 0.0192 | 0.0016 | 66.7% |
| 合计 | 0.0267 | 0.0024 | 100% |

Pro 是 Flash 的 0.0267÷0.0024 = **11.1 倍**。注意结构差异：Pro 的缓存折扣是 12 倍（12÷1），Flash 只有 5 倍（1÷0.2），所以 Flash 的费用更集中在输出（66.7%），Pro 的缓存优化空间更大。

**反推：输出从 800 压到 400。**

- Pro：输出费 0.0096，总费用 0.0015 + 0.0060 + 0.0096 = **0.0171 元**，省 0.0096 元，降幅 **36.0%**。
- Flash：输出费 0.0008，总费用 **0.0016 元**，省 0.0008 元，降幅 **33.3%**。

只降 36% 而不是 50%，因为输入那 0.0075 元是固定成本。按 1000 次这样的请求算，Pro 省 9.6 元。这解释了为什么“控制输出长度”有效，但不能指望它把账单砍半。

**再补一个对照：如果完全没有缓存。** 2000×12 ÷ 1e6 = 0.024 元，加输出 0.0192，总费用 **0.0432 元**。缓存省了 0.0165 元，是无缓存账单的 **38.2%**，也是当前账单的 **61.8%**。注意这两个百分比的分母不同：71.9% 是当前账单内部的构成，38.2% 是相对无缓存账单的降幅，不能相加。

## 4. 代码逐行

```python
P = {"hit": 1, "miss": 12, "out": 24}        # ① 元/百万 token，V4-Pro
n_hit, n_miss, n_out = 1500, 500, 800        # ② usage 返回的三个计数
cost = (n_hit*P["hit"] + n_miss*P["miss"]
        + n_out*P["out"]) / 1_000_000        # ③ 统一除以百万
blended = cost / (n_hit+n_miss+n_out) * 1e6  # ④ 混合单价 9.54
share_out = n_out*P["out"]/1e6/cost          # ⑤ 输出占比 71.9%
```

① 三行价目表就是全部定价逻辑，没有隐藏项；② 对应 API 响应的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens`；③ 单位换算是最容易错的一步，元/百万 要除 1e6，不是除 1000；④ 混合单价只能用于横向比较，不能反过来报价；⑤ 占比决定优化方向。

配套的 `token_cost.py` 解决的是“②从哪来”的前半段：`analyze_text()` 用 `len(tokenizer.encode(text))` 得到 token 数，并打印 token/字符比。但要注意它的价格表是 `price_per_token` 命名、实际按每千 token 使用（`tokens * price / 1000`），单位是美元，和本篇的“元/百万”不是一套口径，不能直接套。它真正的价值是提醒你：中文、代码、JSON、URL 的 token 效率差异很大，估算成本必须用目标模型的分词器或 API 返回的 usage。

## 6. 类比拆解

| 原文类比 | 它映射到哪一步 | 这个比喻在哪儿会失效 |
|---|---|---|
| 一次性给厨师 100 份食材，流水线处理 | Prefill 并行处理全部输入 | 厨房可以临时加灶台、提前备菜，Prefill 的并行度受矩阵规模和算力上限约束，不能随 token 数无限加速 |
| 50 个灶台每次只炒一个菜 | Decode 时 GPU 核心大量闲置 | 真实服务会用 continuous batching 同时炒很多桌的菜，把利用率拉回来；所以单价差距不是 100 倍，而是 2 倍 |
| 缓存是“已经算过，直接拿” | 前缀 K/V 复用，跳过 Prefill | 它只支持严格前缀，不能随机读取中间段落；改一个字全失效，还有几分钟到几十分钟的 TTL，不是数据库缓存 |
| 翻译助手的 System Prompt 不变 | 多轮对话命中缓存 | 多轮里前缀是累积的，只要在中间插入一条新消息，后面的缓存就断了；它不是“相同句子”匹配，而是“相同前缀”匹配 |

## 7. 五个误区

❌ 按 token 计费是商家把定价搞复杂 → ✅ 它是唯一与计算量线性对应的单位 → 因为按次会让长文亏本，按字会让中英文成本错位，token 才是模型的真实工作量。

❌ 输入 token 比输出多，所以输入更贵 → ✅ 比的是单价不是总量 → 因为定价按单位资源消耗，不按账单行的大小；输出单价高 2 倍，总量再少也能反超。

❌ 输出单价是输入的 2 倍，成本就差 2 倍 → ✅ 每 token 占用的 GPU 时间差约 100 倍（50ms vs 5000ms 每千 token） → 因为价格是竞争和补贴后的结果，2 倍是市场价，不是成本比。

❌ 缓存命中省的是存储费 → ✅ 省的是整段 Prefill 的算力 → 因为 K/V 已经在显存或高速存储里，连 Q/K/V 投影和 FFN 都不用跑。

❌ 改几个字，缓存还能部分命中 → ✅ 前缀一断，从第一个不同 token 起全部失效 → 因为第 4 篇的因果注意力里，后面每个位置的 K/V 都依赖它前面的全部位置。

❌ 用字数乘一个系数就能估成本 → ✅ 必须用目标模型 tokenizer 或 usage 字段 → 因为中文、代码、JSON、URL 的 token/字符比差异极大，同一个模型不同内容类型也能差 2 倍以上。

## 9. 自测 8 题（含答案要点）

**概念题**

1. 为什么按 token 而不是按调用次数计费？
   **答案要点**：计算量与 token 数成正比；“你好”和一万字长文的资源消耗差几个数量级，按次收费无法覆盖成本。

2. 输入和输出为什么要分开计价？
   **答案要点**：Prefill 并行、算力密集、利用率高；Decode 串行、带宽密集、利用率低，单位 token 占用的 GPU 时间不同。

3. 缓存命中为什么能便宜一个数量级？
   **答案要点**：前缀的 K/V 已经算好，直接读取，跳过整段 Prefill 的投影、Attention 和 FFN，只付存储与读取成本。

4. 为什么改一个字符就会让缓存全部失效？
   **答案要点**：因果注意力下每个位置的 K/V 依赖前面所有位置；前缀第一个 token 变了，后面全部要重算。

5. 混合单价有什么用？不能用来做什么？
   **答案要点**：用于横向比较不同请求结构的实际成本；不能反推官方报价，也不能用于跨模型比较，因为价目结构不同。

6. 为什么 Agent 场景特别适合前缀缓存？
   **答案要点**：System Prompt 和工具 JSON Schema 每次调用完全相同，且调用密集、间隔短，正好落在缓存 TTL 内。

**计算题**

7. 输入 10,000 token（8,000 命中、2,000 未命中），输出 500 token，用 V4-Pro 算总价与输出占比。
   **答案要点**：8000×1÷1e6 = 0.008；2000×12÷1e6 = 0.024；500×24÷1e6 = 0.012；合计 **0.044 元**；输出占 0.012÷0.044 = **27.3%**。

8. 同一请求如果缓存全部失效（10,000 全按未命中，输出仍 500），费用变成多少、是原来的几倍？
   **答案要点**：10000×12÷1e6 = 0.12；加 0.012 得 **0.132 元**；0.132÷0.044 = **3.0 倍**，缓存贡献了三分之二的费用。

## 10. 一页速记

- 计费单位是 token，因为计算量只跟 token 数走。
- 输入 = Prefill，并行、算力密集、便宜。
- 输出 = Decode，串行、带宽密集、贵。
- V4-Pro 三档：1 / 12 / 24 元每百万 token。
- 输出单价是输入的 2 倍，但占用 GPU 时间约 100 倍。
- 示例账单 0.0267 元，输出 token 占 29%、费用占 72%。
- 缓存只认严格前缀，改一个字全部失效。
- 缓存有 TTL，密集调用才省得到钱。
- 输出砍半只省 36%，因为输入是固定成本。
- Agent 的 10 步任务可能烧掉单轮对话的 20–50 倍。

三个关键数字：**12 倍**（Pro 的缓存折扣）、**72%**（输出占费用比例）、**24 元**（Pro 输出单价，每百万 token）。
