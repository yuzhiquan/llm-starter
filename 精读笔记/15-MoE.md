# 第 15 篇精读｜MoE：把"知道多少"和"算得多快"拆开卖

> 原文：llm-15-moe.md ｜ 前置：第 14 篇 ｜ 核心一句话：MoE 只把每层的 FFN 从一个换成几十个、每个 token 只走其中两个，于是总参数决定知识容量、激活参数决定推理成本，两者第一次被解耦。

## 0. 三句话抓住它

- 总参数是仓库面积，激活参数是每次取货的量。
- 算力只按激活参数付，显存必须按总参数付。
- 30 倍参数差买到的是容量，不是 30 倍速度。

## 1. 这一篇在补哪个洞

这是番外篇五，挂在正篇第五篇（Transformer 全景：FFN 是知识库）之后，同时接第九篇 Scaling Law。正篇把 FFN 讲成"一层一个、所有 token 共用"的知识库，读者自然会把"参数量"等同于"能力"也等同于"成本"。

它补的第一个洞，是参数表上两个数字看起来自相矛盾。如果能力随参数增长，1.6T 应该强得离谱；如果成本随参数增长，1.6T 应该贵得离谱。现实是又强又便宜，说明"参数量"这个词被拆成了两个不同的量，而正篇的 Dense 视角看不见这个拆分。

它补的第二个洞，是全书第一次出现"存储与计算解耦"。前面十篇里，参数存在哪、算力花多少、显存占多少，永远是同一个数字。MoE 把这三件事拆开后，"模型有多大"这个问题本身就不再只有一个答案。

## 2. 概念逐层拆

### 2.1 Expert（专家）

**是什么**：一个结构标准、权重独立的 FFN：W₁ 升维 → GELU → W₂ 降维，和正篇第五篇那个 FFN 一模一样。

**为什么需要**：单个 FFN 扩容会让每个 token 都付全额算力；拆成多个才能"按需取用"，把容量和计算分开。

**在系统里的位置**：替换 Transformer 层里唯一的 FFN 位置，Attention、LayerNorm、残差连接全部不动。

**记住这个数**：64 个专家，每个都和被替换掉的那个 FFN 同样大小。

### 2.2 Router（路由器）

**是什么**：一个线性层 + Softmax + Top-k，输入当前 token 的向量，输出 k 个专家编号及其权重。

**为什么需要**：需要有人决定"这个 token 该查哪本参考书"，而且这个决定必须可微、能跟着主目标一起训练。

**在系统里的位置**：在 Attention 之后、FFN 之前，是 MoE 层唯一的新增组件，参数量占比极小。

**记住这个数**：输出 64 个分数，只取最高的 2 个。

### 2.3 总参数 / 激活参数

**是什么**：总参数 = 所有专家 + 共享部分，决定显存；激活参数 = 单个 token 实际参与计算的参数，决定 FLOPs。

**为什么需要**：把"知道多少"和"算得多快"这两个原本绑死的量拆开，才能独立定价、独立扩展。

**在系统里的位置**：一个记在显存账本上，一个记在算力账本上；只有在 Dense 模型里两者恰好相等。

**记住这个数**：总 1.6T / 激活 49B，比值 32.65×。

### 2.4 Top-k 与加权合并

**是什么**：取分数最高的 k 个专家，把它们的输出按 Softmax 归一化后的权重求和。

**为什么需要**：硬选 1 个既不可微也不稳定；加权合并让梯度能流回 Router，同时平滑输出。

**在系统里的位置**：MoE 层的最后一步，输出维度与单个 FFN 完全一致，因此可以无缝替换。

**记住这个数**：top-2 时输出 = w₁·E₁(x) + w₂·E₂(x)，且 w₁ + w₂ = 1。

### 2.5 负载均衡损失

**是什么**：一个辅助 loss，惩罚"token 全挤在少数专家"的分配方式。

**为什么需要**：Router 会自我强化——越常用的专家训练越充分、越容易被再次选中，最终大量专家变成死参数。

**在系统里的位置**：只加在训练目标上，推理时不参与任何计算。

**记住这个数**：训练目标 = 下一 token 预测 loss + α × 负载均衡 loss。

### 2.6 专家并行与 All-to-All

**是什么**：把不同专家放在不同 GPU 上，token 通过 All-to-All 通信发送到专家所在卡，算完再传回。

**为什么需要**：1.6T 参数单卡装不下，必须切分；按专家切比按层切更自然，因为专家之间本就独立。

**在系统里的位置**：在 MoE 层内部引入一次跨卡往返，是 MoE 相对 Dense 多出来的固定开销。

**记住这个数**：每个 MoE 层两次 All-to-All（发出去、收回来）。

### 2.7 稀疏度

**是什么**：激活参数 ÷ 总参数，衡量"这次用了多大比例"。

**为什么需要**：它是 MoE 最核心的超参，同时决定"省多少算力"和"浪费多少显存"。

**在系统里的位置**：由专家数 E 和 top-k 共同决定，稀疏度 = k / E。

**记住这个数**：64 选 2 → 3.125%；49B / 1.6T → 3.06%。

## 3. 手算推演

题设：Dense 7B 对比 MoE（总 1.6T / 激活 49B）；fp16 每参数 2 字节；每层 64 专家选 2。

**Step 1：单 token 计算量**

- Dense 7B：约 2 × 7B = **14 GFLOPs/token**。
- MoE：约 2 × 49B = **98 GFLOPs/token**。
- 比值 98 / 14 = **7×**。

结论：MoE 的单 token 计算量是 7B 的 7 倍——它比 7B **慢**，不是快。

**Step 2：显存需求**

- Dense：7B × 2B = **14 GB**。
- MoE：1.6T × 2B = 3200 GB = **3.2 TB**。
- 比值 3200 / 14 = **228.6×**。
- 换成 80GB H100：3200 / 80 = **40 张**，仅装权重，不含 KV Cache 与激活值。

**Step 3：FFN 的激活比例**

每层 64 选 2，FFN 部分实际参与计算的比例 = 2 / 64 = **3.125%**，即存储的专家参数有 96.875% 在这一个 token 上是闲置的。

参数占比推算（设 FFN 占总量 95%，共享部分占 5%）：

- Dense 7B：FFN 约 4.67B，存储占比 66.7%（按 2/3 估），激活占比同为 66.7%。
- MoE：专家 FFN 存储 1.6T × 95% = 1.52T，占比 95%；单 token 激活的 FFN = 1.52T × 3.125% = **47.5B**，仍占激活参数的绝对大头。
- 关键不是"占比变了"，而是"**存储的 FFN ÷ 激活的 FFN = 1 / 3.125% = 32×**"。

**Step 4：三个数字对不上，以原文为准**

严格列式：设共享参数 S、专家参数 E，则 S + E = 1600B，S + E/32 = 49B。两式相减得 E × (31/32) = 1551 → E = 1601B，S = **−1B**，无解。

再看比例：49 / 1600 = **3.06%**，而 2 / 64 = **3.125%**——激活占比反而略低于纯专家路由比例，这在数学上要求共享参数为负。

结论：1.6T、49B、64 选 2 这组数字是教学取整，三者不能同时严格成立。真实配置里专家数、top-k、共享专家配比会让它自洽（对照：DeepSeek-V3 是 256 选 8 + 1 个共享专家，37B / 671B = 5.5%）。本篇一律以原文口径 1.6T / 49B 为准。

**Step 5：对比表**

| 维度 | Dense 7B | MoE 1.6T / 49B | 比值 |
|---|---|---|---|
| 总参数 | 7B | 1600B | 228.6× |
| 激活参数 | 7B | 49B | 7× |
| 单 token FLOPs | 14 GFLOPs | 98 GFLOPs | 7× |
| fp16 权重显存 | 14 GB | 3200 GB | 228.6× |
| 80GB 卡（仅权重） | 1 张 24GB 卡即可 | 40 张 | — |
| 知识容量 | 7B 级 | 1.6T 级 | 228.6× |
| 相对 1.6T Dense | — | 快 32.65× | — |
| 部署门槛 | 单卡 | 多机多卡 + All-to-All | — |

**Step 6：为什么"30 倍"不等于"快 30 倍"**

1. 32.65× 是"总参数 ÷ 激活参数"，是容量与算力的解耦倍数，不是任何速度比。
2. 速度要看跟谁比：相对 1.6T Dense 快 32.65×，相对 7B Dense 是**慢 7×**。基准一换，结论反转。
3. MoE 省算力但**不省显存**：3.2TB 要 40 张卡起，7B 一张 24GB 卡就够。
4. Decode 是访存瓶颈（番外二）：时间 ∝ 需要读的权重字节数。MoE 每 token 要读 49B 的权重（98GB），已经是 7B（14GB）的 7 倍，这是物理下限。
5. 再叠加 All-to-All 通信、负载不均衡（最忙的专家决定整层延迟）、路由 kernel 启动，实测加速只会比理论更差。

一句话：MoE 用 **228× 的显存** 换 **228× 的容量**，只付 **7× 的算力**——赚的是容量性价比，不是速度。

## 4. 代码逐行

原文给了 Router 的简化实现，以下 14 行按其结构复现并标注。

```python
def moe_layer(x, experts, W_gate, k=2):
    scores = matmul(x, W_gate)            # 1. 线性层给 64 个专家打分
    top_v, top_i = topk(scores, k)        # 2. 取分数最高的 2 个（不可微）
    w = softmax(top_v)                    # 3. 只对选中的 2 个分数归一化
    out = zeros_like(x)                   # 4. 输出缓冲，维度与 x 一致
    for j in range(k):                    # 5. 只跑被选中的专家
        out += w[j] * experts[top_i[j]](x)  # 6. 加权累加，权重和为 1
    aux = k * sum(frac_i * mean_score_i)  # 7. 负载均衡辅助损失
    return out, aux
```

逐行对应：

- 第 1 行：Router 本体，只是一个 768×64 的矩阵乘，参数量可忽略。
- 第 2 行：Top-k 是硬选择，本身没有梯度，梯度靠第 6 行的权重回传。
- 第 3 行：注意是**对 top-k 的分数**做 Softmax，不是对全部 64 个，否则权重和不为 1。
- 第 5 行：循环只跑 2 次，这就是 3.125% 的物理来源；其余 62 个专家连读都不读。
- 第 7 行：辅助 loss，训练时防止路由坍缩，推理时直接丢弃。
- 全局：Attention、LayerNorm、残差完全没出现在这个函数里——MoE 的改动范围就这么大。

## 5. 数字与公式速查

| 量 | 值 | 含义/出处 |
|---|---|---|
| 总参数 | 1.6T | 原文口径，含全部 64 个专家 |
| 激活参数 | 49B | 原文口径，单 token 实际计算 |
| 总/激活 | 32.65× | 1600 / 49，原文称"30 多倍" |
| 专家数 / top-k | 64 / 2 | 原文第二节 |
| FFN 激活比例 | 3.125% | 2 / 64 |
| 激活占总参数 | 3.06% | 49 / 1600 |
| 与 7B 算力比 | 7× | 49 / 7 |
| 与 7B 显存比 | 228.6× | 3200 GB / 14 GB |
| MoE 权重显存 | 3.2 TB | 1.6T × 2 字节 |
| 80GB 卡需求 | 40 张 | 3200 / 80，仅权重 |

核心公式：

- 稀疏度 = k / E
- 单 token FLOPs ≈ 2 × 激活参数
- 权重显存 = 总参数 × 每参数字节数
- 训练目标 = 主 loss + α × 负载均衡 loss

## 6. 类比拆解

| 原文类比 | 它映射到哪一步 | 这个比喻在哪儿会失效 |
|---|---|---|
| 大型图书馆：藏书量 vs 每次翻几本 | 总参数决定知识容量，激活参数决定单次计算量 | 图书馆书再多也不会让找书变慢；MoE 的显存占用和跨卡通信随总参数线性上涨，容量是有代价的 |
| 全科医生 vs 大医院分诊 | Dense 一个 FFN 通吃，MoE 用 Router 分诊 | 分诊台是人工规则、可解释、可纠错；Router 是学出来的连续打分，可能把感冒分到心外科，且没有转诊机制 |
| 餐厅引导客人均匀入座 | 负载均衡损失 | 餐厅可以拒绝或排队；Router 的均衡只是软约束，靠 loss 惩罚，推理时依然可能倾斜 |

## 7. 五个误区

❌ 1.6T 参数就要 1.6T 的算力 → ✅ 单 token 只算 49B → 因为 Router 只激活 top-k 专家，其余权重不参与任何矩阵乘。

❌ MoE 比 Dense 7B 快 → ✅ 单 token 算力是 7B 的 7 倍，其实更慢 → 因为"快 32 倍"的基准是 1.6T Dense，不是 7B，基准选错结论就反了。

❌ 激活参数小，所以显存也小 → ✅ 显存按总参数算，要 3.2TB → 因为不知道下一个 token 会路由到哪个专家，64 个必须全部常驻。

❌ 专家是按领域人工划分的 → ✅ 分工是训练中自发形成的，且不可解释 → 因为 Router 只优化下一 token 预测，没有任何"地理""语法"标签。

❌ 专家越多模型一定越强 → ✅ 超过临界点后路由会坍缩、通信成瓶颈 → 因为负载均衡是软约束，专家越多每个专家分到的 token 越少、训练越不充分。

## 9. 自测 8 题（含答案要点）

**1. 概念：MoE 改了 Transformer 的哪个部分？**
答：只改 FFN。Attention、LayerNorm、残差连接全部保持不变，把单个 FFN 换成 E 个专家 + 一个 Router。

**2. 概念：为什么总参数决定显存，激活参数决定算力？**
答：所有专家都可能被下一个 token 选中，必须全部常驻显存；但任一 token 只走 top-k 个专家，矩阵乘只发生在被选中的权重上。

**3. 概念：Router 的梯度是怎么回传的？**
答：Top-k 选择本身不可微，梯度通过被选中专家的加权系数 w 回传，w 来自对 top-k 分数的 Softmax，因此 Router 能学到"给谁高分"。

**4. 概念：负载均衡损失解决什么问题？**
答：防止路由坍缩。若不约束，少数专家会被越选越强、其余专家收不到梯度而退化，最终有效专家数远小于 64。

**5. 概念：为什么 MoE 的推理速度不能按"总参数/激活参数"来估算？**
答：这个比值只描述容量与算力的解耦程度。真实速度还要看基准模型、显存带宽、All-to-All 延迟和最忙专家的负载。

**6. 概念：同样激活 49B，MoE 和 Dense 49B 的能力差别从哪来？**
答：参数量。MoE 有 1.6T 的存储容量去记知识，只是每次只调用一小部分；Dense 49B 的全部知识必须挤在 49B 权重里。

**7. 计算：某 MoE 总参数 800B，其中专家 FFN 760B、共享部分 40B，64 选 2。求激活参数、稀疏度、改成 top-4 后的激活参数、fp16 显存与 80GB 卡数。**
答：激活 = 40 + 760 × 2/64 = 40 + 23.75 = **63.75B**；稀疏度 = 63.75/800 = **7.97%**；top-4 时 = 40 + 47.5 = **87.5B**（10.9%）；显存 = 800 × 2 = **1600GB**，80GB 卡需 **20 张**（仅权重）。

**8. 计算：Dense 13B 对比 MoE（总 600B / 激活 30B），fp16。求显存比、单 token FLOPs 比、"总/激活"倍数，并说明哪个数字最能代表真实速度差。**
答：显存 600/13 = **46.2×**；FLOPs 30/13 = **2.31×**；总/激活 = 600/30 = **20×**。最能代表真实速度差的是 2.31×（还要再打折于通信开销）；20× 只是解耦倍数，46.2× 是显存代价。

## 10. 一页速记

- MoE 只改 FFN 一个位置，其余原封不动。
- 64 个专家，每个 token 只走 2 个。
- 总参数决定显存，激活参数决定算力。
- 1.6T 存储，49B 计算，比值 32.65×。
- 单 token 98 GFLOPs，是 7B 的 7 倍。
- 显存 3.2TB，是 7B 的 228.6×。
- FFN 激活比例 2/64 = 3.125%。
- 存储/激活 = 32×，这是 MoE 的全部魔法。
- 30 倍是容量倍数，不是速度倍数。
- 代价是显存、All-to-All 和负载均衡。
- 专家分工是学出来的，不是人分的。

关键数字：**3.125%**、**7×**、**3.2TB**。
