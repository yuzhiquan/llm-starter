# 第 16 篇精读｜算子：大模型最小的施工单位和最大的隐藏成本

> 原文：llm-16-operators.md ｜ 前置：第 15 篇 ｜ 核心一句话：模型的所有"智能"最终都落成十几种算子的重复调用，而速度不取决于算子个数，取决于每个算子要搬多少次数据。

## 0. 三句话抓住它

- 算子是"输入→固定规则→输出"的一步计算，不是数学理论。
- 一层 20 个、32 层 645 个，一次前向就这么多。
- 真正的瓶颈是搬运，不是计算；融合才是加速来源。

## 1. 这一篇在补哪个洞

这是番外篇六，挂在正篇第五篇（Transformer 全景）和第四篇（Attention）之后，向上接番外篇二（GPU 与显存带宽）。正篇十篇讲的都是"数学上发生了什么"：矩阵乘、Softmax、残差。但它从没回答"这些数学在机器上以什么为单位被执行"。

它补的第一个洞是**落地层**。同一串公式，拆成 20 个独立算子执行，和融合成 5 个算子执行，数学结果一样、速度差 2–4 倍。不懂这一层，就无法解释为什么"优化一个算子"能让整个模型快 30%。

它补的第二个洞是**新闻解读能力**。"XX 框架优化了 Attention 算子""该芯片支持 200+ 种算子""FlashAttention 是高效注意力算子"——这些句子的主语全是算子。不知道算子是什么，就只能把这些话当广告听。

它补的第三个洞是**祛魅**。把一次前向拆到 645 个算子后会发现，大模型做的每一步（查表、乘加、取指数）用计算器都能完成。让它显得智能的不是单个算子，而是第六篇训练出来的那些参数。

## 2. 概念逐层拆

### 2.1 Operator（算子）

**是什么**：一个明确的"输入张量 → 固定计算规则 → 输出张量"步骤，例如 MatMul、Softmax、LayerNorm、GELU。

**为什么需要**：它是框架调度和硬件执行的最小语义单位；再往下就只剩线程、寄存器和内存地址，不再有模型层面的意义。

**在系统里的位置**：夹在 PyTorch 的计算图和 CUDA kernel 之间，是"模型代码"与"硅片"之间的翻译层。

**记住这个数**：全书出现的算子种类约 15 种，却被调用几百次。

### 2.2 Kernel

**是什么**：某个算子在特定硬件上的一段编译好的实现代码。

**为什么需要**：同一个 Softmax 在 NVIDIA、昇腾、Apple M 系列上必须各有一份 kernel，否则跑不起来。

**在系统里的位置**：算子是对外接口，kernel 是对内实现，一对多。

**记住这个数**：一个算子可以有几十个 kernel 变体（不同 dtype、不同 shape、不同布局）。

### 2.3 算子融合

**是什么**：把多个小算子合并进一个 kernel，中间结果留在 SRAM/寄存器，不写回 HBM。

**为什么需要**：HBM 带宽远比算力稀缺，搬运一个 S² 矩阵的时间可能超过计算它的时间。

**在系统里的位置**：发生在图优化/编译阶段，数学等价，执行路径完全不同。

**记住这个数**：FlashAttention 把 5 个 Attention 算子合成 1 个，S² 的 HBM 往返从 4 次降到 0 次。

### 2.4 Memory-bound（访存瓶颈）

**是什么**：当计算时间小于数据搬运时间时，性能由带宽决定而不是由 FLOPS 决定。

**为什么需要**：这是解释"为什么融合能加速"的唯一原因，也是 Decode 阶段慢的根本原因。

**在系统里的位置**：算术强度（FLOPs/Byte）低于硬件的算力带宽比时，就落入这个区间。

**记住这个数**：H100 约 990 TFLOPS fp16 ÷ 3.35 TB/s ≈ 295 FLOPs/Byte，低于它的算子都是访存瓶颈。

### 2.5 FlashAttention

**是什么**：一种 IO 感知的 Attention 实现，用分块（tiling）+ 在线 Softmax 避免把 S² 矩阵完整写回显存。

**为什么需要**：长序列下 S² 矩阵既占显存又占带宽，是 Prefill 阶段的主要瓶颈。

**在系统里的位置**：属于 kernel 层优化，完全不影响 Attention 的数学定义。

**记住这个数**：S=4096、d=128 时，HBM 搬运从 138.4 MB 降到 4.2 MB。

### 2.6 算子库

**是什么**：硬件厂商提供的算子实现集合，如 CUDA/cuBLAS/cuDNN、昇腾 CANN、ROCm。

**为什么需要**：芯片能不能跑大模型，取决于算子库的覆盖度和关键算子的效率，而不是纸面峰值算力。

**在系统里的位置**：位于框架和驱动之间，是硬件生态真正的护城河。

**记住这个数**：支持 200+ 算子只是入场券，MatMul、Softmax、Attention 三个的效率才决定成败。

## 3. 手算推演

**Step 1：逐个数一层**

| # | 算子 | 作用 |
|---|---|---|
| 1 | LayerNorm | 稳定输入分布 |
| 2 | MatMul (Q) | 生成 Query |
| 3 | MatMul (K) | 生成 Key |
| 4 | MatMul (V) | 生成 Value |
| 5 | Reshape | 拆成多头 |
| 6 | Transpose | 对齐维度 |
| 7 | MatMul (QKᵀ) | 算注意力分数 |
| 8 | Scale | 除以 √d |
| 9 | Mask | 未来位置置 −∞ |
| 10 | Softmax | 分数变概率 |
| 11 | MatMul (AV) | 加权聚合 Value |
| 12 | Transpose | 合并多头 |
| 13 | Reshape | 还原形状 |
| 14 | MatMul (W_O) | 输出投影 |
| 15 | Add | 残差 1 |
| 16 | LayerNorm | FFN 前归一化 |
| 17 | MatMul (W₁) | FFN 升维 |
| 18 | GELU | 非线性 |
| 19 | MatMul (W₂) | FFN 降维 |
| 20 | Add | 残差 2 |

**一层 = 20 个算子。**

**Step 2：乘以层数**

- 32 层：20 × 32 = **640 个**。
- 首尾：Embedding 1 + 位置编码 Add 1 + 最终 LayerNorm 1 + LM Head MatMul 1 + 最终 Softmax 1 = **5 个**。
- 合计：640 + 5 = **645 个算子/token**，口语说"约 650 个"。

**Step 3：和原文"约 500 个"对账**

原文口径是每层约 15 个、32 层约 480 个、加首尾约 500 个。差的 5 个/层来自计数口径：

- QKV 三个 MatMul 在生产中被融合成 1 个 fused QKV 投影：20 − 2 = 18。
- Reshape / Transpose 是视图操作（view），不产生独立 kernel：18 − 4 = 14。
- 原文另计入 1 个 Concat（多头拼接）：14 + 1 = 15。

所以 **20 是"数学步骤"口径，15 是"实际 kernel"口径**，两者都对，取决于你数的是算子还是 kernel。这个差别本身就是本篇的核心结论：**算子数 ≠ kernel 数**。

**Step 4：FlashAttention 的访存账**

设序列长度 S = 4096，head 维度 d = 128，fp16 每元素 2 字节。

- S² = 4096² = 16,777,216 个元素 = **33.55 MB**（单份）。
- 标准实现分三步：
  1. `S = QKᵀ`：读 Q、K（各 S·d），**写 S²** → 1 次写；
  2. `P = softmax(S)`：**读 S²**，**写 P** → 1 读 1 写；
  3. `O = PV`：**读 P**，读 V，写 O → 1 次读。
- S² 相关搬运合计 **4 份 = 134.2 MB**。
- Q/K/V/O 合计 4 × S·d = 2,097,152 元素 = **4.19 MB**。
- 标准总计 **138.4 MB**。

融合后：S² 全程留在 SRAM，HBM 只读写 Q/K/V/O = **4.19 MB**。

- 减少：(138.4 − 4.19) / 138.4 = **96.97%**，约 97%。
- 倍数：138.4 / 4.19 = **33×**。
- 按 3.35 TB/s：41.3 μs → **1.25 μs**。

**Step 5：为什么实测只快 2–4 倍**

Attention 的浮点计算量：两次 MatMul，各 2S²d FLOPs，合计 4S²d = 4 × 16,777,216 × 128 = **8.59 GFLOP**。按 990 TFLOPS 算约 **8.7 μs**。

- 标准：max(计算 8.7, 访存 41.3) = **41.3 μs**（访存瓶颈）。
- 融合后：max(8.7, 1.25) = **8.7 μs**（变成计算瓶颈）。
- 理论上限加速：41.3 / 8.7 = **4.75×**。

再考虑 occupancy 上不去、Softmax 的 exp 开销、SRAM 容量限制，实测落在 2–4×，与原文"快了 2-4 倍"吻合。

**Step 6：一个反例**

Decode 阶段每次只有 1 个 Query token，S² = 1，融合几乎零收益。FlashAttention 的红利全在 Prefill 的长序列上。这解释了为什么"首 token 延迟"和"逐 token 生成速度"是两个必须分开优化的指标。

## 4. 代码逐行

原文无脚本，以下 15 行伪代码复现一层 Transformer 的算子序列，行尾编号对应 Step 1 的清单。

```python
def layer(x, cache=None):
    h = layernorm(x, g1, b1)                    # 1
    q, k, v = matmul(h, Wq), matmul(h, Wk), matmul(h, Wv)   # 2-4
    q, k, v = split_heads(q, k, v)              # 5 Reshape + 6 Transpose
    s = matmul(q, k.transpose(-1, -2))          # 7 QKᵀ
    s = s / sqrt(d)                             # 8 Scale
    s = mask_future(s)                          # 9 因果掩码
    p = softmax(s, dim=-1)                      # 10
    o = matmul(p, v)                            # 11 AV
    o = merge_heads(o)                          # 12 Transpose + 13 Reshape
    x = x + matmul(o, Wo)                       # 14 W_O + 15 Add
    h = layernorm(x, g2, b2)                    # 16
    f = gelu(matmul(h, W1))                     # 17 + 18
    x = x + matmul(f, W2)                       # 19 + 20
    return x
```

逐行对应：

- 第 1 行 LayerNorm：每层两次，是仅有的非矩阵类重活。
- 第 2–4 行：三个 MatMul，生产中通常融合成一个 QKV 投影。
- 第 5–6 行：Reshape/Transpose 只改元数据，不搬数据，但会打断融合。
- 第 7 行 QKᵀ：产出 S²，是整层显存占用的峰值来源。
- 第 8–10 行：Scale、Mask、Softmax 三步都读写同一块 S²，是融合的首要目标。
- 第 11 行 AV：S² 在这里被第二次读，融合后这次读也省掉。
- 第 14–15 行：输出投影 + 残差，残差是纯 element-wise，成本低但必须同步。
- 第 17–19 行：FFN 的两个 MatMul 占全层参数量的三分之二，是算力主战场。

融合版本只需把 7–11 行替换成一行 `o = flash_attn(q, k, v, causal=True)`，算子数从 20 降到 16，但真正省下的是 s、p 两块 S² 不再落 HBM。

## 5. 数字与公式速查

| 量 | 值 | 含义/出处 |
|---|---|---|
| 每层算子数 | 20 | 本篇按数学步骤细数 |
| 原文每层算子数 | 约 15 | 原文口径（融合后） |
| 32 层算子数 | 640 | 20 × 32 |
| 首尾算子数 | 5 | Embedding、位置 Add、LN、LM Head、Softmax |
| 单 token 总算子 | 645 | 640 + 5，原文口径约 500 |
| S² 矩阵大小 | 33.55 MB | S=4096，fp16 |
| 标准实现搬运 | 138.4 MB | 4 份 S² + Q/K/V/O |
| 融合后搬运 | 4.19 MB | 只剩 Q/K/V/O |
| 搬运减少 | 96.97% | (138.4−4.19)/138.4 |
| 理论加速上限 | 4.75× | 41.3 μs / 8.7 μs |
| 实测加速 | 2–4× | 原文口径 |
| H100 算力带宽比 | ≈295 FLOPs/Byte | 990 TFLOPS / 3.35 TB/s |

核心公式：

- 算术强度 = FLOPs ÷ Bytes，低于 295 即访存瓶颈
- 标准 Attention S² 搬运 = 4 × S² × 2 字节
- 融合后搬运 = 4 × S × d × 2 字节
- 融合收益比 ≈ 1 + S/(2d)

验算：S=4096、d=128 时 1 + 4096/256 = 17，与实际 33× 同量级（差异来自是否计入 Roofline 的理想化）。

## 6. 类比拆解

| 原文类比 | 它映射到哪一步 | 这个比喻在哪儿会失效 |
|---|---|---|
| 最小施工单位 | 算子是不可再分的最小计算单位 | 施工单位不会彼此合并，算子会（融合）；融合后"最小单位"的边界就变了，20 个算子可能只发 16 个 kernel |
| 软件和硬件之间的合同 | 框架发算子请求，硬件提供 kernel | 合同是死的，算子库却有版本、覆盖缺口和精度差异；同一个 Softmax 在不同芯片上的数值行为并不完全一致 |
| 查表、乘矩阵、取指数，计算器都能做 | 算子都是初等运算 | 单步确实简单，但 645 个算子 × 1100 个 token 的调度、并行、访存协同，完全不是计算器可类比的事 |

## 7. 五个误区

❌ 算子是很高深的数学 → ✅ 就是 MatMul、Add、exp 这类初等步骤 → 因为复杂的不是单步，而是规模、组合和访存。

❌ FlashAttention 是一种新的 Attention 算法 → ✅ 数学上完全等价，只是 IO 优化的 kernel → 因为结果几乎逐位相同，变的只是数据搬了多少次。

❌ 算子越多模型越强 → ✅ 算子种类基本固定，强弱由参数决定 → 因为结构只是十几种算子的重复，容量全在权重里。

❌ 算子融合会改变计算结果 → ✅ 数学等价，只有浮点累加顺序带来的微小差异 → 因为融合改的是执行顺序，不是公式。

❌ 算子数量等于 kernel 数量 → ✅ 20 个算子可能只发 16 个 kernel，也可能因为 shape 拆分发得更多 → 因为融合与切分都会改变这个映射。

## 9. 自测 8 题（含答案要点）

**1. 概念：算子和 kernel 的区别是什么？**
答：算子是对外的语义接口（"做一次 MatMul"），kernel 是它在某块硬件上的具体实现。一个算子对应多个 kernel 变体，融合后多个算子又可对应一个 kernel。

**2. 概念：为什么说大模型的瓶颈常常不是算力？**
答：很多算子的算术强度低于硬件的算力带宽比（H100 约 295 FLOPs/Byte），此时时间花在等数据搬运，而不是等计算单元。

**3. 概念：FlashAttention 改变了 Attention 的数学吗？**
答：没有。它用分块 + 在线 Softmax 避免物化 S² 矩阵，结果与标准实现等价，改变的是 HBM 往返次数。

**4. 概念：Reshape 和 Transpose 为什么常被排除在算子计数之外？**
答：它们只改张量的元数据（shape、stride），不搬动数据、不产生独立 kernel，实际代价接近零。

**5. 概念：为什么原文说 15 个/层，本篇数出 20 个/层？**
答：口径不同。原文按融合后的 kernel 计（QKV 合一、忽略视图操作），本篇按数学步骤计。两者相差 5 个，正好是 2 个 MatMul + 4 个视图操作 − 1 个 Concat。

**6. 概念：为什么 Decode 阶段用 FlashAttention 收益很小？**
答：Decode 每次只有 1 个 Query token，S² = 1，没有可省的 S² 搬运；它的瓶颈是逐 token 读取全部权重，属于另一种访存问题。

**7. 计算：48 层模型，每层 22 个算子，首尾 6 个。求一次前向的算子数，以及生成 300 个 token 的总算子调用次数。**
答：每 token = 48 × 22 + 6 = **1062 个**；300 token = 1062 × 300 = **318,600 次**。

**8. 计算：S=2048、d=64、fp16。求标准 Attention 的 S² 相关搬运量、总搬运量、融合后搬运量、减少比例，并判断是计算瓶颈还是访存瓶颈。**
答：S² = 4,194,304 元素，4 份 = 16,777,216 × 2B = **33.55 MB**；4Sd = 524,288 × 2B = **1.05 MB**；总计 **34.6 MB**；融合后 **1.05 MB**；减少 **96.97%**。计算量 4S²d = 1.07 GFLOP，算术强度 1.07e9 / 34.6e6 ≈ **31 FLOPs/Byte**，远低于 295，属于**访存瓶颈**。

## 10. 一页速记

- 算子 = 输入到输出的一个确定计算步骤。
- 全书只有十几种算子，被重复几百次。
- 一层 20 个（数学口径），32 层 645 个。
- 原文 15 个/层是融合后口径，差在 QKV 合并与视图操作。
- 算子数 ≠ kernel 数，这是两本账。
- 瓶颈通常在搬运，不在计算。
- FlashAttention 不改数学，只改 IO。
- S² 的 HBM 往返从 4 次降到 0 次。
- 搬运减少 97%，实测加速 2–4 倍。
- Decode 阶段 S=1，融合几乎无收益。
- 智能来自参数，不来自算子。

关键数字：**645**、**4→0**、**97%**。
